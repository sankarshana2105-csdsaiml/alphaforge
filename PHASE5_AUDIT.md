# Phase 5 Research and Leakage Audit

| Area | Status | Evidence | Risk | Mitigation | Residual limitation |
|---|---|---|---|---|---|
| A. Target leakage | CONTROLLED | Targets are built in `targets.py`; feature/target columns are separate and future/target names are rejected. | A mislabeled custom oracle column could bypass name-based guards. | Keep target construction isolated; run synthetic future-feature traps. | Column provenance is not cryptographically enforced. |
| B. Feature leakage | CONTROLLED WITH RESIDUAL RISK | Phase 1 features are trailing; mutation tests prove future rows do not change earlier features. | Manually supplied custom features may be incorrectly declared safe. | Use only declared Phase 1 features and reject future/target/raw columns. | External feature provenance still requires review. |
| C. Rolling-window leakage | PASS | All rolling calculations are trailing and never centered. | A future feature edit could introduce centered windows. | Retain future-mutation and rolling-boundary tests. | Code review remains necessary for new features. |
| D. Scaling/preprocessing leakage | PASS | Fresh pipelines fit inside every training fold; scaler means are tested against fold-train means. | Future preprocessing additions could be performed globally. | Require every learned transform to live inside the fold pipeline. | Stateless feature computation still assumes bar data are available at prediction time. |
| E. Train/test temporal leakage | PASS | Chronological folds require unique increasing timestamps and train end before evaluation start. | Incorrect timestamp semantics from a vendor can defeat ordering. | Validate timestamp meaning and retain overlap assertions. | Exchange publication latency is not modeled. |
| F. Horizon-boundary leakage | PASS | Exactly `horizon` candidate rows are purged before every evaluation window. | Irregular data gaps may require time-based rather than row-based embargoes. | Match configured and target horizons; test target source positions. | Row purging assumes one target step per validated row. |
| G. Hyperparameter/tuning leakage | PASS | Models use fixed conservative parameters; no search observes future folds. | Human iteration after reading results can become informal tuning. | Freeze choices before final evaluation and log later experiments. | Researcher degrees of freedom remain. |
| H. Threshold-selection leakage | PASS | Only predeclared 0.50/0.55/0.60 thresholds are reported as sensitivity analysis. | Selecting the best reported threshold afterward would contaminate inference. | Report every threshold and reserve new data for any selection. | No threshold is validated for deployment. |
| I. Regime-definition leakage | PASS WITH CAUTION | Volatility and trend regimes use trailing features available at each row. | Simple binary labels can overstate economic meaning. | Call them descriptive labels and report all regimes with sample counts. | Regime definitions are heuristic and asset-dependent. |
| J. Final-test contamination | CONTROLLED | Walk-forward evaluation is fixed and does not tune on evaluation folds. | Repeated human inspection can indirectly influence later choices. | Treat current OOS history as consumed and reserve a future lockbox period. | No untouched external lockbox dataset is included. |
| K. Survivorship bias | OPEN LIMITATION | The pipeline makes no claim that symbol selection is survivorship-free. | Current constituents can inflate historical results. | Use point-in-time universes and delisted assets for multi-asset studies. | Depends on future data source. |
| L. Corporate-action assumptions | OPEN LIMITATION | OHLCV validation checks bar consistency but not adjustment quality. | Splits and dividends can create false returns and volatility. | Require documented adjusted prices and independently verify large jumps. | Vendor adjustment methodology is external. |
| M. Vendor/data-cleaning artifacts | OPEN LIMITATION | Missing and duplicate policies are explicit and invalid bars fail cleanly. | Bad ticks, timezone errors, and vendor backfills may remain. | Version raw data and compare suspicious observations across vendors. | No vendor-specific quality audit exists yet. |
| N. Multiple-testing/data-snooping | OPEN LIMITATION | Sensitivity grids are intentionally small and all outcomes must be reported. | Repeated horizons, windows, features, and models inflate false discovery risk. | Pre-register comparisons, correct inference when expanded, and use new data for confirmation. | Current metrics are descriptive, not significance claims. |

## Audit conclusion

The implemented pipeline controls direct temporal, target, rolling, preprocessing, and horizon-boundary leakage. It does not eliminate external dataset bias, informal researcher tuning, or multiple-testing risk. Suspicious performance must be independently reproduced on newly acquired point-in-time data before interpretation.
